# FSM Editor for Visual Studio

Visual Studio 2022+ extension (VSIX): a visual editor for UML 2.5.1 state machines. A machine is two JSON files: `X.fsm`, the model (no ids: elements are identified by their names), and `X.fsm.layout`, the drawing. The model file's format is fsm-cli's (its README, its schema and test cases); the layout file's is fsm-editor-common's (its `schemas/fsm-layout.schema.json`). Files of earlier versions are XMI 2.5.1 with UML DI: they are read, and converted when saved. It is the Visual Studio edition of FSM Editor for VS Code (`../fsm-editor-vscode`): same concepts, rules and messages. Reading and writing the files, converting old ones, validation, the grammar's checks, comparing, merging and code generation are fsm-editor-common's (`../fsm-editor-common`, Rust), run as a sidecar process (`fsm-editor-common serve`); this edition keeps the UI, the diagram's geometry and editing (C#, a port of the VS Code edition's webview), and Visual Studio's integration.

## Commands

```sh
dotnet build                 # all projects; VSIX packaging (VSSDK, vsct) only on Windows
dotnet test                  # test/FsmEditor.Core.Tests; GeometryTests compares SvgExport with geometry/, a copy of the VS Code edition's reference SVGs (its test/unit/fixtures/geometry); ClipboardTests copies and reads the clipboard JSON of clipboard/, a copy of its test/unit/fixtures/clipboard; EditingCasesTests runs the steps of editing/, a copy of its test/unit/fixtures/editing, on DiagramSession (the drags as DiagramCanvas does them) and must write its files; ContrastTests checks Contrast (the signal colors made readable on the default themes); ListingTests checks the Marketplace listing (vsixmanifest limits, VSPackage.resx, the overview's links)
scripts/fetch-common.sh      # or scripts\fetch-common.ps1: copy fsm-editor-common's sidecar, fsm-cli's templates, schemas/ and api-cases/ (from ../fsm-editor-common + ../fsm-cli, --build to build it first, or unpacked release archives) into src/FsmEditor.Vsix/cli (gitignored); the tests need the sidecar
```

`test/FsmEditor.IntegrationTests` (net48, Windows only, skipped unless `FSM_VS_INTEGRATION=1`): tests inside Visual Studio. `VisualStudio.cs` starts the latest Visual Studio's experimental instance (`/rootsuffix Exp`) on copies of the examples, reaches its DTE through the Running Object Table (an STA thread with a message filter), gives real mouse and keyboard input, and finds the diagram through UI Automation (`DiagramCanvas`'s automation id `FsmDiagramCanvas`). `.github/workflows/integration.yml` runs them on the self-hosted Windows runner (a logged-in desktop) after installing this commit's VSIX into the experimental instance; never for pull requests. Microsoft's `[IdeFact]` harness (vs-extension-testing) is archived and stops at Visual Studio 2022.

`.github/workflows/ci.yml` runs on every push: the Core tests, the VSIX build, and the VSIX installed quietly into the runner's Visual Studio (VSIXInstaller), found among its extensions, and uninstalled.

F5 in Visual Studio (startup project FsmEditor.Vsix) starts the experimental instance; try `examples/MediaPlayer.fsm` and `examples/Order.fsm` (uses `Payment.fsm` as a submachine).

On macOS or Linux, `dotnet test` covers `FsmEditor.Core`, and `dotnet build` in `src/FsmEditor.Vsix` compiles the VSIX's C# (with the threading analyzers) but not `VSCommandTable.vsct` or the package. The VSIX runs only on Windows, so a change under `src/FsmEditor.Vsix` can't be tried there: keep it small, mirror the JetBrains edition's equivalent code where there is some, and tell the user what to check in the experimental instance.

## Architecture

- `src/FsmEditor.Core` (netstandard2.0, no VS references, testable anywhere) holds all the logic:
  - `Model.cs`: `FsmModel`, a flat vertex list where `Parent` is a region id, or a state id for border vertices (entry/exit points of a state, connection point references). Entry/exit points whose parent is a top-level region are the machine's own connection points. `ModelIndex` gives tree navigation.
  - `Common.cs`: the client of fsm-editor-common's sidecar: started on first use from `Common.ExecutablePath` (the extension's `cli\fsm-editor-common.exe`; the tests: `FSM_EDITOR_COMMON`, else what `scripts/fetch-common.sh` copied), one JSON request per line, answered in order, one at a time (a lock), started again when it exits. `ModelJson.cs`: the model as the JSON the sidecar takes and gives (the VS Code edition's model; vertices and transitions as `ClipboardJson` writes them).
  - Facades over the sidecar, keeping their signatures: `Format.cs` (`ReadMachine`, `WriteMachine`, which gives generated names and resolves references, `DerivedIds`; the small helpers stay here), `MachineFiles.cs` (a document's state), `Conversion.cs` (old files), `Load.cs` (either format), `Validation.cs`, `Expressions.cs` (the grammar's checks, normalized text), `Compare.cs`, `Merge.cs`. `Num.cs`: numbers as JavaScript writes them.
  - Staying here: `Contrast.cs` (WCAG ratios; a signal color moved toward the foreground until readable, which `Theme.Mark` and `Theme.TextOf` apply for problems and the Trace Player), `Labels.cs` (transition label syntax, its parts checked through `Expressions`), `Geometry.cs` (compartments, regions, routes, labels), `DiagramSession.cs` (every editing operation, raising `Committed`), `Tools.cs`, `SvgExport.cs`, `ClipboardJson.cs` (same clipboard JSON as VS Code, and a small JSON reader), `Workspace.cs` (hrefs, machine summaries, submachine resolution), `Sessions.cs` (the logic of the diff and merge panes, a port of the VS Code edition's `sessions.ts`), `Extraction.cs`, `Trace.cs` (the Trace Player: log formats, replay, and `TraceSession`, the logs, timeline and cursor; a port of the VS Code edition's `src/trace/`).
- `src/FsmEditor.Vsix` (net48, Community.VisualStudio.Toolkit):
  - `FsmEditorFactory` creates `FsmEditorPane` over an `FsmDocument` (`IVsPersistDocData2`, `IPersistFileFormat`): the document data holding the two files' texts and the model, with its own history of states, which the diagram's undo and redo walk; Visual Studio's save, Save As, dirty mark and close act on it, and it follows its files on disk when it has no changes of its own. Saving writes both files (an unreadable layout file is replaced only after asking); saving an old file converts the files linked to it. A text editor can't share it: Open as Text closes the diagram first (asking about unsaved changes). `.fsm` and `.fsm.layout` files open as JSON in the text editor (`Services/ContentTypes.cs`), old files in the XML editor. Each new document state is debounced, validated off the UI thread against the machines found by `FsmWorkspace` (solution folder, open diagrams' unsaved states preferred), then handed to `EditorControl.Update` (`null` model when it is the diagram's own edit) and the Error List (`Diagnostics`, at the lines the writer or reader gives).
  - `Editor/DiagramSessions.cs`: Compare as Diagrams (a version from Git, written read-only under `%LOCALAPPDATA%\FsmEditor\Compare`, beside the file) and the merge of a file with conflicts (its sides beside it, read-only), linking the panes through Core's `DiffSession`/`MergeSession`; `Services/Git.cs` runs git.
  - `Editor/`: WPF built in code (no XAML). `DiagramCanvas` renders in `OnRender` and hit-tests geometrically; `PropertiesPanel` rebuilds itself per selection; `Theme` maps VS theme colors.
  - Edit commands (Undo/Redo/Cut/Copy/Paste/Delete/Select All) arrive as VS commands in `FsmEditorPane`'s `IOleCommandTarget`; a focused text box gets them instead of the diagram.
  - `TracePlayer/`: `TracePlayerService` runs a `TraceSession` (file watchers on the logs, play timer, machines of the solution and open documents) and hands each open diagram its `TraceView`, drawn by `DiagramCanvas`; `TracePlayerWindow` is the tool window.
  - `CodeGen/CodeGenerator.cs`: code generation through the sidecar's `generate` (fsm-cli's generator): the machine's text and those of its submachines (from disk, transitively), the template's text, `/`-separated paths (`/C:/work/Order.fsm`); the files that come back are written into the output folder, the problems go to the Error List. The release workflow bundles `fsm-editor-common.exe`, fsm-cli's templates and the schemas in `src/FsmEditor.Vsix/cli/`, from the fsm-editor-common release pinned by `FSM_COMMON_VERSION`, and runs the tests with its interface's cases. `FsmEditorPackage.GenerateCodeAsync` is the whole flow.

## Project rules

- Keep parity with the VS Code extension for the UI: editor behavior, clipboard JSON. The file format, the grammar, validation, conversion, comparing and merging are fsm-editor-common's and fsm-cli's: don't reimplement them here; change them there (fsm-cli, then fsm-editor-common), then fetch the sidecar again (`scripts/fetch-common.sh --build`) and run `dotnet test`. `Geometry.cs` mirrors `media/editor.js` of the VS Code edition: compare it by hand. `../fsm-editor-jb` ports this Core to Kotlin file for file, so a Core change goes there next.
- **Text grammar:** behaviors are argument-less calls separated by `;`; conditions combine calls with `!`, `&&`, `||` and parentheses; `else` only on choice/junction branches; triggers are event names or `after(<number><ms|s|m|h>)`. The editor refuses invalid text, and the validator reports it.
- **Out of scope:** state machine extension/inheritance and the transition-oriented notation.
- Don't reimplement code generation: templates and the code model belong to fsm-cli.
- `.fsm` files hold no model hash: fsm-cli computes it from the file.
- Core must not reference Visual Studio assemblies. VS code must respect the threading analyzers (the build has no warnings).
- User-facing docs: `README.md`, `docs/UML-CONFORMANCE.md` (update when behavior or rules change), `docs/CODEGEN.md`.
