# FSM Editor for Visual Studio

Visual Studio 2022+ extension (VSIX): a visual editor for UML 2.5.1 state machines. A machine is two JSON files: `X.fsm`, the model (no ids: elements are identified by their names), and `X.fsm.layout`, the drawing. The model file's format is fsm-cli's (its README, its schema and test cases); the layout file's is the editions' own, defined by the VS Code edition (its `docs/UML-CONFORMANCE.md`, "The layout file", and `schemas/fsm-layout.schema.json`, copied here). Files of earlier versions are XMI 2.5.1 with UML DI: they are read, and converted when saved. It is the Visual Studio edition of FSM Editor for VS Code (`../fsm-editor-vscode`): same concepts, file format, rules and messages, reimplemented in C# (no JavaScript is reused). Code generation runs `fsm write`, the Rust command-line tool of `../fsm-cli`, with Jinja templates.

## Commands

```sh
dotnet build                 # all projects; VSIX packaging (VSSDK, vsct) only on Windows
dotnet test                  # test/FsmEditor.Core.Tests
scripts/fetch-cli.sh         # or scripts\fetch-cli.ps1: copy fsm.exe + templates, schemas/ and cases/ (from ../fsm-cli, or unpacked release archives) into src/FsmEditor.Vsix/cli (gitignored); the tests need cases/
```

F5 in Visual Studio (startup project FsmEditor.Vsix) starts the experimental instance; try `examples/MediaPlayer.fsm` and `examples/Order.fsm` (uses `Payment.fsm` as a submachine).

On macOS or Linux, `dotnet test` covers `FsmEditor.Core`, and `dotnet build` in `src/FsmEditor.Vsix` compiles the VSIX's C# (with the threading analyzers) but not `VSCommandTable.vsct` or the package. The VSIX runs only on Windows, so a change under `src/FsmEditor.Vsix` can't be tried there: keep it small, mirror the JetBrains edition's equivalent code where there is some, and tell the user what to check in the experimental instance.

## Architecture

- `src/FsmEditor.Core` (netstandard2.0, no VS references, testable anywhere) holds all the logic:
  - `Model.cs`: `FsmModel`, a flat vertex list where `Parent` is a region id, or a state id for border vertices (entry/exit points of a state, connection point references). Entry/exit points whose parent is a top-level region are the machine's own connection points. `ModelIndex` gives tree navigation.
  - `Json.cs` + `Format.cs`: the file format. The JSON reader and the model reader are fsm-cli's (`json.rs`, `format.rs`), ported through the VS Code edition's `json.ts`/`format.ts`: the same problems, messages, lines and derived ids. `Format.cs` also reads and writes the layout file (relative positions, automatic places), writes both files deterministically (`WriteMachine`: write(read(x)) = x, byte-identical to the VS Code edition), gives generated names (`AssignNames`) and the ids fsm-cli gives (`DerivedIds`). `MachineFiles.cs`: a document's state (the two texts and the model) and writing a model into one (an edit the format can't hold is refused).
  - `Xmi.cs` + `XmlTree.cs`: reading old files (XMI 2.5.1 with UML DI); `Conversion.cs` converts them, a group linked by submachines at a time. Nothing writes XMI. `Load.cs`: a model from a file's text, either format.
  - `Compare.cs` (matching by name, the changes), `Merge.cs` (conflict markers, taking one side's version of an element), `Sessions.cs` (the logic of the diff and merge panes): ports of the VS Code edition's `compare.ts`, `merge.ts` and `sessions.ts`.
  - `Validation.cs`, `Expressions.cs` (text grammar), `Labels.cs` (transition label syntax), `Geometry.cs` (compartments, regions, routes, labels; also used to convert the UML DI region shapes of old files), `DiagramSession.cs` (every editing operation, raising `Committed`), `Tools.cs`, `SvgExport.cs`, `ClipboardJson.cs` (same clipboard JSON as VS Code), `Workspace.cs` (hrefs, machine summaries, submachine resolution), `Trace.cs` (the Trace Player: log formats, replay, and `TraceSession`, the logs, timeline and cursor; a port of the VS Code edition's `src/trace/`).
- `src/FsmEditor.Vsix` (net48, Community.VisualStudio.Toolkit):
  - `FsmEditorFactory` creates `FsmEditorPane` over an `FsmDocument` (`IVsPersistDocData2`, `IPersistFileFormat`): the document data holding the two files' texts and the model, with its own history of states, which the diagram's undo and redo walk; Visual Studio's save, Save As, dirty mark and close act on it, and it follows its files on disk when it has no changes of its own. Saving writes both files (an unreadable layout file is replaced only after asking); saving an old file converts the files linked to it. A text editor can't share it: Open as Text closes the diagram first (asking about unsaved changes). `.fsm` and `.fsm.layout` files open as JSON in the text editor (`Services/ContentTypes.cs`), old files in the XML editor. Each new document state is debounced, validated off the UI thread against the machines found by `FsmWorkspace` (solution folder, open diagrams' unsaved states preferred), then handed to `EditorControl.Update` (`null` model when it is the diagram's own edit) and the Error List (`Diagnostics`, at the lines the writer or reader gives).
  - `Editor/DiagramSessions.cs`: Compare as Diagrams (a version from Git, written read-only under `%LOCALAPPDATA%\FsmEditor\Compare`, beside the file) and the merge of a file with conflicts (its sides beside it, read-only), linking the panes through Core's `DiffSession`/`MergeSession`; `Services/Git.cs` runs git.
  - `Editor/`: WPF built in code (no XAML). `DiagramCanvas` renders in `OnRender` and hit-tests geometrically; `PropertiesPanel` rebuilds itself per selection; `Theme` maps VS theme colors.
  - Edit commands (Undo/Redo/Cut/Copy/Paste/Delete/Select All) arrive as VS commands in `FsmEditorPane`'s `IOleCommandTarget`; a focused text box gets them instead of the diagram.
  - `TracePlayer/`: `TracePlayerService` runs a `TraceSession` (file watchers on the logs, play timer, machines of the solution and open documents) and hands each open diagram its `TraceView`, drawn by `DiagramCanvas`; `TracePlayerWindow` is the tool window.
  - `CodeGen/FsmCli.cs` runs `fsm write <file> --template <jinja> --out <dir>` and parses `wrote …` lines, `file:line: severity: message` problems and fsm's own `fsm: …` messages (shown when it fails, such as a template it refuses). The release workflow bundles `fsm.exe`, its templates and the format's schemas in `src/FsmEditor.Vsix/cli/`, from the windows-x64 and schemas archives of the fsm-cli release pinned by `FSM_CLI_VERSION`, and runs the tests against its cases archive. `FsmEditorPackage.GenerateCodeAsync` is the whole flow.

## Project rules

- Keep parity with the VS Code extension: text grammar, validation rules and messages, file format (both files, byte for byte), clipboard JSON. The model file's reader and validator are checked against fsm-cli's test cases (`CasesTests.cs`, from `src/FsmEditor.Vsix/cli/cases`), the layout reader against the VS Code edition's layout test files (`fixtures/layout`). `test/FsmEditor.Core.Tests/fixtures` holds reference results from the VS Code edition, shared with the JetBrains edition: regenerate them from the umbrella repo with `node parity/fixtures.mjs` when the reference changes (see fixtures/README.md), and check the three editions write the same files with `node parity/check.mjs`. `Geometry.cs` mirrors `media/editor.js` of the VS Code edition: compare it by hand. `../fsm-editor-jb` ports this Core to Kotlin file for file, so a Core change goes there next.
- **Text grammar:** behaviors are argument-less calls separated by `;`; conditions combine calls with `!`, `&&`, `||` and parentheses; `else` only on choice/junction branches; triggers are event names or `after(<number><ms|s|m|h>)`. The editor refuses invalid text, and the validator reports it.
- **Out of scope:** state machine extension/inheritance and the transition-oriented notation.
- Don't reimplement code generation: templates and the code model belong to fsm-cli.
- `.fsm` files hold no model hash: fsm-cli computes it from the file.
- Core must not reference Visual Studio assemblies. VS code must respect the threading analyzers (the build has no warnings).
- User-facing docs: `README.md`, `docs/UML-CONFORMANCE.md` (update when behavior or rules change), `docs/CODEGEN.md`.
